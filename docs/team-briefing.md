## 0. 오늘 우리가 만드는 것 — 한 문장

**PRD 문서 하나를 넣으면, AI가 단계를 밟아 Penpot 디자인을 만들어내는 자동 파이프라인.**

디자인을 손으로 그리는 날이 아닙니다. **디자인을 그리는 기계를 만드는 날**입니다.
디자인은 그 기계를 실행해서 나옵니다.

### 헷갈리기 쉬운 지점

| 오해 | 실제 |
|---|---|
| "내가 Penpot에서 화면을 예쁘게 그리면 되는구나" | ❌ 아닙니다. 그건 채점 안 됩니다 |
| "AI한테 '디자인 만들어줘' 하면 되는구나" | ❌ 그게 안 되니까 하네스를 만드는 겁니다 |
| "AI가 단계를 밟도록 **지침 문서**를 쓰는 날이구나" | ✅ 이게 맞습니다 |

**오늘 우리가 주로 만지는 건 Penpot이 아니라 마크다운 파일입니다.**

---

## 1. 하네스가 뭔가요

AI에게 그냥 "디자인 만들어줘"라고 하면, **아는 걸로 일단 결과물부터** 만듭니다.
중간 과정이 없으니 품질이 떨어집니다.

사람은 그렇게 안 합니다. 여행 계획을 예로 들면:

```
1. 목적·예산·체력 고려해서 큰 행선지를 잡고
2. 빈 곳에 취향에 맞는 목적지를 거리·예산 따져 배치하고
3. 진짜 갈 만한 곳인지 조사해서 검증하고
4. 그제서야 계획이 완성됩니다
```

**이 단계를 AI에게 강제하는 장치가 하네스입니다.** 그래서 "개목줄"이라고들 부릅니다.

### 하네스의 구성 요소 — 3개만 알면 됩니다

| 구분 | 경로 | 역할 |
|---|---|---|
| **Sub Agent** | `.claude/agents/stage-*.md` | **각 단계를 정의.** 오늘 우리가 만드는 것의 90% |
| **CLAUDE.md / AGENTS.md** | 루트 | 항상 적용되는 지침 |
| **Skill** | `.claude/skills/` | 특정 상황에만 쓰는 지침 |

> 💡 **Sub Agent끼리는 기억을 공유하지 않습니다.**
> 그래서 단계 간 전달은 **반드시 파일로** 합니다. 이게 오늘 규칙 1번인 이유입니다.

## 2. 우리 조 설계 — 8단계

```
                    ┌─ ② 기존파일 실측 ─┐
        ① PRD 해석 ─┤                    ├─→ ④ 토큰 → ⑤ 컴포넌트 저작
                    └─ ③ 화면목록 도출 ─┘                    ↓
                                        ⑦ 시각 QA ← ⑥ 화면 저작
                                             ↓
                                        ⑧ 최종 검증
```

| # | 단계 | 하는 일 | 남기는 파일 |
|---|---|---|---|
| ① | `stage-1-prd-parse` | PRD를 읽어 기계가 쓸 수 있는 명세로 변환 | `01-prd-spec.md` |
| ② | `stage-2-audit-existing` | 기존 디자인 Page를 **실제로 읽어** 색·폰트·간격 측정 | `02-design-audit.md` |
| ③ | `stage-3-screen-plan` | 만들 화면 목록을 PRD에서 **계산** | `03-screen-list.md` |
| ④ | `stage-4-tokens` | 디자인 토큰을 JS 상수로 확정 | `04-tokens.md` |
| ⑤ | `stage-5-components` | Penpot에 **컴포넌트부터** 만듦 | `05-components.md` + Penpot |
| ⑥ | `stage-6-author-screens` | 컴포넌트를 **조립해서** 화면 저작 | `06-screens.md` + Penpot |
| ⑦ | `stage-7-visual-qa` | PNG로 뽑아서 **눈으로 확인** → 수정 지시 | `07-qa.md` |
| ⑧ | `stage-verify-penpot` | 진짜 다 있는지 되읽어 검증 | `99-verify.md` |

### 왜 이렇게 나눴는지 (심사위원이 묻는 지점입니다)

- **②③이 병렬** — "기존에 뭐가 있나"와 "뭘 만들 건가"는 서로 독립입니다. 병렬 구간이 있다는 것 자체가 의존관계를 이해했다는 증거입니다.
- **④가 ②③을 합류** — 토큰은 *기존에서 뽑은 값*이면서 *만들 화면이 필요로 하는 값*이어야 합니다.
- **⑤와 ⑥을 분리** — ⭐ 가장 중요합니다. 합치면 AI는 **반드시 복사·붙여넣기를 합니다.** 컴포넌트를 먼저 만들게 강제해야 "라이브러리 재사용" 점수가 나옵니다.
- **⑦이 독립 단계** — 안 보고 쌓으면 마지막에 전부 어긋나 있습니다.

## 3. 조 편성 — 2인 1조 × 3개조

| 조 | 담당 단계 | 성격 | 왜 이 짝인가 |
|---|---|---|---|
| **A조**<br>조장 + 1 | ① PRD해석<br>③ 화면목록<br>⑧ 최종검증 | **논리 · 계약** | 계약이 흔들리면 전부 무너집니다. 공용 파일은 조장이 관리합니다 |
| **B조**<br>2명 | ② 기존파일 실측<br>④ 토큰 | **디자인 감각** | 색·타이포 판단이 필요합니다. 디자이너가 있는 조로 |
| **C조**<br>2명 | ⑤ 컴포넌트<br>⑥ 화면 저작 | **Penpot 저작** | 함정과 가장 많이 싸우는 자리. AI 리터러시 높은 분이 |
| **전원** | ⑦ 시각 QA | **교차 검토** | 자기 화면은 자기가 못 봅니다 |

> ⑦을 전원 순환으로 두는 이유가 하나 더 있습니다.
> 채점축에 **"협업의 흔적"**이 있습니다. 교차 검토 기록이 그 증거가 됩니다.

### 각 조가 실제로 하는 일

**A조** — `stage-1`, `stage-3`, `stage-verify` 세 파일을 고도화합니다.
PRD의 문장을 빠짐없이 화면 목록으로 환원시키는 게 핵심입니다.
"최소 3개"를 목표로 잡으면 3개만 나옵니다. 유저스토리·상황 절을 훑어 **빈 상태·로딩·실패까지** 화면으로 세게 만드세요.

**B조** — `stage-2`, `stage-4` 두 파일을 고도화합니다.
AI는 놔두면 **자기 취향의 색**을 씁니다. 기존 Page를 실제로 읽어 HEX를 뽑아내게 만드는 게 핵심입니다. PRD가 "톤앤매너 유지"를 요구하는데, 대부분의 팀이 여기서 무너집니다.

**C조** — `stage-5`, `stage-6` 두 파일을 고도화합니다.
오늘 가장 오래 걸리는 자리입니다. 아래 6번 함정 표를 agent 본문에 그대로 박아 넣고 시작하세요.

## 5. 규칙 — 이것만 지키면 충돌이 안 납니다

```
1. 단계 간 통신은 파일로만. "앞 단계가 말해줬다"는 없다.
   (Sub Agent는 기억을 공유하지 않습니다)

2. 앞 단계 산출물이 없으면 즉시 중단 + 보고. 추측해서 채우지 않는다.

3. ⭐ 고유명사 금지.
   "당근"·"에어비앤비"·"주식"·"소개팅"이 agent 본문에 등장하면 그건 버그다.
   대신 "PRD 2절이 지정한 Page", "PRD 7절이 나열한 화면"으로 쓴다.

4. 화면 개수를 숫자로 박지 않는다. ③이 계산한 결과를 따른다.

5. 작업 Page 이름은 인자로 받는다. 못 받으면 되묻고 멈춘다.

6. 남의 stage 파일 수정 금지. 필요하면 조장에게.
```

### 3번이 왜 그렇게 중요한가

**심사용 PRD는 미공개입니다.** 당근·에어비앤비가 아닌 제3의 PRD가 들어옵니다.
특정 PRD에 맞춘 지침은 그 자리에서 무너집니다.

채점축 B의 핵심이 **재현성**입니다. 고도화하다 보면 무심코
"당근처럼 따뜻한 톤으로" 같은 문장을 씁니다. 반드시 나옵니다.

> 조장이 16:00에 이걸 한 번 돌립니다:
> ```bash
> grep -ri "당근\|airbnb\|에어비앤비\|주식\|소개팅" .claude/
> ```
> 걸리면 그 자리에서 고칩니다.

## 6. 🔴 Penpot 함정 — C조는 반드시, 나머지도 훑어보세요

운영이 리허설하며 **실제로 부딪힌** 것들입니다. 모르면 시간을 통째로 날립니다.

### 저작 agent 본문에 그대로 박아 넣을 것

| 함정 | 대응 |
|---|---|
| `penpot.openPage()`가 **다음 호출까지 유지 안 됨** | 모든 스크립트 **첫 줄에서 작업 Page를 다시 고정** |
| `openPage()` 한 **그 호출 안에서** 새 Page 노드를 만지면 죽음 | Page 전환은 **별도 호출**로 먼저 |
| figma 형식 `fills`는 **인스턴스에서 막힘** | penpot 형식 `{fillColor:"#RRGGBB", fillOpacity:1}` 만 사용 |
| 컴포넌트 **이름 변경·자식 remove** → 플러그인 멈춤 | 이름·구조는 **처음에 확정.** 잘못 만들었으면 새 이름으로 새로 |
| 컴포넌트 이름이 **파일 전역** — 옆 조 것이 잡힘 | 이름 + **id 프리픽스**로 좁혀 찾기 |
| hHug 프레임 안 텍스트가 **아래가 잘린 채** 굳음 | 화면 완성 후 `growType==="auto-height"` 텍스트를 전부 `resize` 재계산 |
| `figma.variables.*`는 성공 응답만 오고 **토큰이 안 남음** | 토큰은 **JS 상수 객체**로. 점수는 컴포넌트로 받는다 |
| 반투명 오버레이가 **렌더링에서 사라짐** | 스크림 대신 **뒤 보드의 `opacity`를 낮춤** |
| `export_shape`가 레이아웃 안정 전에 찍히면 **빈 영역** | 없다고 판단하기 전에 **재-export 한 번** |

### 알아두면 좋은 것

- **실제 사진 삽입 가능** — `await penpot.uploadMediaUrl(name, url)` → `rect.fills = [{fillOpacity:1, fillImage: img}]`
- **`shape.clone()` 됩니다** — 모달·에러·로딩 같은 상태 변형은 복제 후 덮어쓰기
- **`board.insertChild(index, node)`** 로 자식 순서 조정 가능
- 인스턴스의 **`characters`(텍스트) 오버라이드 됩니다** — 데이터만 다른 행은 인스턴스 재사용

## 7. 🔴 작업 Page 규칙 — 이건 운영 규칙입니다

**실시간 협업입니다. 엉뚱한 Page에 그리면 그 즉시 남의 작업 위에 덮습니다.**

| Page | 규칙 |
|---|---|
| `{내 이름}` | **여기서만 저작합니다** |
| 기존 자산 Page | **읽기 전용.** 수정 금지 |
| `중간공유` · `최종제출` | 공용. 결과를 **옮겨 담는** 곳. 여기서 처음부터 저작 금지 |

- 저작 전 **작업 Page 이름을 반드시 확정**합니다
- 기본값으로 첫 Page를 쓰지 않습니다
- 읽기만 할 때는 **Page를 전환하지 않습니다** (전환하면 남이 보는 화면도 바뀝니다)

단계 분할의 타당성 · 단계 간 계약의 명료성 · **재현성(반하드코딩)** ·
**지침의 구체성** · 협업의 흔적

> 🎯 **재현성**과 **지침의 구체성**이 이 행사가 실제로 묻는 질문입니다.

우리 8단계 설계가 각 축을 어떻게 노리는지:

| 축 | 우리 설계의 대응 |
|---|---|
| 단계 분할 | ②③ 병렬, ④ 합류 — 의존관계를 이해한 분할 |
